# Migrate from v2 to v3

Compared with v2, the v3 version mainly deletes some outdated functions and configuration items, and also changes the default value of the plug-in, making the overall plug-in easier to use and easier to install.
If you don't use any complicated custom configuration, you can upgrade smoothly.

## Configuration item changes

### Deleted configuration items

- Delete the `replaceUniversalSelectorWith` option and use `cssSelectorReplacement.universal` instead. The latter parameter overrides the former.
- Delete the `minifiedJs` option. Now it fully follows the user's configuration. If the user compresses, it will compress, and vice versa.
- Removed the `jsEscapeStrategy` option, now there is only one mode by default `replace`/`regenerate` mode is no longer provided
- Delete the `customReplaceDictionary` mode of
- `cssMatcher`/`htmlMatcher`/`jsMatcher`/ To be compatible with the original `mainCssChunkMatcher` expression, you can use `wxsMatcher` to convert the `glob` expression into a regular expression to be compatible with the original configuration
- `cssPreflightRange` only exists in one mode, which is `all`. The previous `view` option is handed over to `cssSelectorReplacement.universal` for hosting

### Added configuration items

- `rem2rpx` : Type `rem2rpx?: boolean | rem2rpxOptions`

rem to rpx configuration, **not enabled** by default, configuration items can be passed in, see https://www.npmjs.com/package/postcss-rem-to-responsive-pixel for configuration items
This configuration item represents that the plug-in has built-in `postcss-rem-to-responsive-pixel`, but it is not enabled by default. Passing in an `true` is equivalent to passing in the configuration:

```js
{
// 32 means 1rem = 32rpx
  rootValue: 32,
// By default all attributes are converted
  propList: ['*'],
// The unit of conversion can be changed to px / rpx
  transformUnit: 'rpx',
}
```

Of course, you can also pass in `rem2rpxOptions` such as `object` for customization

#### Why is it not enabled by default?

1. In order to smoothly transition from `2.x` version to `3.x`
2. From my perspective, although the overall integration level of the built-in `postcss` plug-in function is higher, it may not be so free for other developers. For example, in the case of `2.x`, since `postcss-rem-to-responsive-pixel` is external, developers can freely decide its loading order and loading logic, but after it is built in, it is all decided by me. But there are also built-in benefits, that is, it can be used right out of the box.

### Enhanced configuration items

- `cssChildCombinatorReplaceValue`, `cssSelectorReplacement.root`, `cssSelectorReplacement.universal` can now accept string arrays, and they can be automatically expanded to prevent selector formatting errors.

### Modified default value

- `cssPreflightRange` changed from `'view'` to `undefined`. Now the role of `all` becomes the selector in the `tailwindcss` variable injection area. Add a selector of
- `cssSelectorReplacement.universal` changes from `'view'` to `['view', 'text']`, which means that the `*` selector will be expanded into `view,text` and the corresponding method
- `cssChildCombinatorReplaceValue` changed from `'view + view'` to `['view']`
- `replaceUniversalSelectorWith`,`jsEscapeStrategy`,`minifiedJs` options were removed so the default values are no longer retained

### Now the options are merged, the default behavior of the array becomes overwriting, originally it was merged

```js
const options = getOptions(input,defaults)
defaults: ['a','b'], input:['c']
// before:
options == ['a','b','c']
// after:
options == ['c']
```
