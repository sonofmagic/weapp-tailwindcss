# Support conclusion for special character class names in uni-app Vite App WebView

The conclusion should be clear first: after ordinary `uni-app Vite` is run into Android/iOS App WebView, the DOM/CSSOM of WebView itself does not completely support `dark:bg-red-300`, `text-[45rpx]` and other classes with `:`, `[`, and `]`. As long as the class enters the DOM as is and the CSS selector does standard CSS escaping, such as `.dark\:bg-red-300`, `.text-\[45rpx\]`, the real WebView can match the style.

However, in the actual build chain of `uni-app Vite + Tailwind CSS + weapp-tailwindcss`, it is not recommended to rely on these raw classes to remain in the final App product. The reason is that the App side also needs to process:

- Vue/uni-app template compiled runtime code
- Selectors and variant selectors generated by Tailwind v4
- `rpx` Length unit classification and unit conversion of any value
- Android/iOS WebView compatibility differences for modern CSS values
- Whether there is a one-to-one correspondence between JS string class and CSS selector

Therefore, `weapp-tailwindcss` will map these class names to safe classes in the ordinary uni-app App WebView branch, and synchronize the JS runtime code with the CSS selector. For example:

| Source code writing | App WebView product class |
| ------------------- | ------------------------- |
| `dark:bg-red-300`   | `dark_cbg-red-300`        |
| `text-[45rpx]`      | `text-_b45rpx_B`          |
| `bg-white/70`       | `bg-white_f70`            |

## This verification environment

`demo/uni-app-vite-tailwindcss-v4` has been run into Android and iOS App respectively, and the output directory is confirmed to be `dist/dev/app-plus`.

| Platform | Runtime                                         | WebView version information                                | Verification conclusion |
| -------- | ----------------------------------------------- | ---------------------------------------------------------- | ----------------------- |
| Android  | HBuilder `15.07` / `1507`, Android 11 emulator  | Android System WebView `com.google.android.webview`        |
| iOS      | HBuilder `15.07` / `1507`, iOS Simulator `26.5` | WKWebView / WebKit bundle `8624.2.5.10.4`, Safari `26.5` / |

Android executes the DOM/CSSOM probe in the real HBuilder App WebView through the WebView remote debugging protocol. The result is:

```json
{
  "rawClassSelectorMatched": true,
  "rawAttributeSelectorMatched": true,
  "rawTextClassSelectorMatched": true,
  "rawTextAttributeSelectorMatched": true,
  "safeDarkMatched": true,
  "safeTextMatched": true
}
```

The `uni-app` App service layer of iOS does not necessarily expose `document`, so the DOM/CSSOM probe on the page will show `document unavailable`. Therefore, iOS also provides the `Special Class Visual Probe` visual probe: it binds the raw class to `view/text` through runtime splicing, and then uses attribute selectors such as `[class~="dark:bg-red-300"]` and `[class~="text-[45rpx]"]` for matching. In the iOS screenshot, the raw dark background turns pink and the raw text changes to 45px, indicating that the view layer can retain and match these raw classes.

## Verification method

The `demo/uni-app-vite-tailwindcss-v4` home page in the repository contains an `Special Class Probe` panel. After running it into an Android or iOS App, the following checks are performed in the real App WebView:

1. Create a raw class element using `document.createElement`:
   - `dark:bg-red-300`
   - `text-[45rpx]`
2. Inject the standard escaped CSS selector:
   - `.dark .dark\:bg-red-300`
   - `.text-\[45rpx\]`
3. Create a safe class control group:
   - `dark_cbg-red-300`
   - `text-_b45rpx_B`
4. Use `getComputedStyle` to read the real rendering results.

The page and console will output:

```text
[uni-app-vite] Special Class Probe
```

If you see:

```text
raw.dark:bg-red-300.matched: true
raw.text-[45rpx].matchedViaEscapedSelector: true
safe.dark_cbg-red-300.matched: true
safe.text-_b45rpx_B.matched: true
```

It means that the App WebView that can currently run DOM/CSSOM probes itself can recognize these raw classes, but only requires the CSS selector to be escaped correctly. If iOS displays `document unavailable`, refer to `Special Class Visual Probe` on the page.

The page also contains `Special Class Visual Probe`. It does not depend on `document` and is used to cover App runtimes such as iOS that do not have a DOM API in the service layer. The probe contains two sets of controls:

- raw group: splice out `dark:bg-red-300` and `text-[45rpx]` at runtime and bind them to page nodes.
- safe group: use `dark_cbg-red-300`, `text-_b45rpx_B` directly.

If both the raw group and the safe group appear with a pink background and 45px large characters, it means that the current App view layer can retain and match the raw class; if only the safe group hits, it means that the raw class cannot be relied upon to directly enter the final product.

## Recommended writing method

The business source code continues to write the original class name of Tailwind:

```html
<view class="theme-dark dark:bg-red-300 text-[45rpx]">
  App WebView
</view>
```

Do not write safe classes in products by hand, and do not mix raw classes and safe classes in business code. The safe class is a build product contract, which is generated and synchronized by `weapp-tailwindcss`.

## Not recommended

Do not force retention of raw classes by turning off `weapp-tailwindcss` or skipping translation:

```ts
// Not recommended: It is easy to cause inconsistent processing of CSS selector, JS class and rpx under App WebView
WeappTailwindcss({
  disabled: process.env.UNI_PLATFORM === 'app',
})
```

The normal uni-app App WebView should continue to retain the plugin and let the generator output compatible CSS according to the WebView branch.

## Troubleshooting criteria

If you see that this type of style does not take effect on the App side, check first in the following order:

1. Check whether the class in `dist/dev/app-plus/app-service.js` has become a safe class.
2. Check whether there is a corresponding safe selector for the final `dist/dev/app-plus/app.css`.
3. See if the color has been downgraded from `oklch()` / `color-mix()` in Tailwind v4 to `rgb()`, `rgba()` or `#hex`.
4. See if `text-[45rpx]` generates the length pattern instead of incorrectly generating `color: 45rpx`.
5. Look at the `Special Class Probe` panel again and distinguish between "WebView itself does not support raw classes" or "the build chain does not align classes with CSS".

## Current conclusion

Based on the actual measurement of `demo/uni-app-vite-tailwindcss-v4` on Android / iOS App WebView, the conclusion is:

- Special characters such as `:`, `[`, and `]` are not strictly prohibited for App WebView.
- raw class is only reliable if the DOM class is preserved at the same time as the escaped CSS selector.
- The iOS App service layer may not have `document`. Do not equate whether the `document.createElement` probe can run with whether the view layer supports special classes.
- In real `uni-app Vite + Tailwind CSS` products, a more stable solution is to use `weapp-tailwindcss` to automatically output safe class.
- Documents, demos, and tests should all assert safe classes as the final product, rather than assuming that raw classes will be retained in the App product.
